# Формат хранилища Graphite (vault) — vault_format 1

**Статус: ЗАМОРОЖЕН.** Этот документ фиксирует формат данных на диске. После первого коммита он не редактируется; любое изменение формата — это `vault_format 2` с отдельным документом и миграцией. Источник требований — `docs/SPEC.md` §6 и реестр решений Р2, Р3, Р8, Р11, Р13, Р22. Золотой набор примеров — `tests/fixtures/vault/` + машинные ожидания `tests/fixtures/expected.json`.

## 1. Принципы

1. **Файлы — единственный источник истины.** Vault — обычная папка с markdown-файлами; всё в `.graphite/` — перестраиваемый кэш.
2. **Совместимость с Obsidian-конвенциями**: frontmatter, `[[wiki-ссылки]]`, `#теги`, `^блочные-якоря`.
3. **Формат рассчитан на «грязных» писателей**: внешний редактор, агент с файловым доступом, скрипты — штатные авторы. Всё, что описано ниже как «валидно», парсер обязан переживать; всё остальное — деградировать мягко, без потери пользовательского текста.
4. **Никакой канонизации при сохранении** (Р8): приложение хранит файл ровно как набран. Переформатирование чужого текста запрещено.

## 2. Кодировка и переводы строк

- Кодировка — **UTF-8**. Приложение пишет без BOM; BOM на чтении допускается и пропускается.
- Файлы, создаваемые приложением, — **LF**. Правка существующего файла сохраняет его текущий стиль конца строки; **чужие CRLF никогда не переписываются молча**.
- Для парсера `\r\n` эквивалентен `\n`; смешанные концы строк в одном файле валидны.
- Unicode-нормализация содержимого не выполняется (текст хранится как введён); NFC применяется только при *сравнении* в резолвинге (§9.3).

## 3. Структура vault на диске

```
Vault/
  .graphite/            служебное: индекс, журнал, история, настройки
  .trash/               мягкое удаление, 30 дней
  _assets/              вложения
  Входящие/
  Journal/2026/07/2026-07-03.md
  Проекты/
    Приложение заметок/
      _index.md
      Идеи/
        _index.md
        Тёмная тема.md
      План MVP.md
```

### 3.1 Служебные папки (Р13)

| Папка | Назначение | Индексация |
|---|---|---|
| `.graphite/` | индекс `index.db`, журнал `journal/`, снапшоты `history/`, настройки | не индексируется как заметки; можно удалить целиком — всё перестраивается |
| `.trash/` | мягко удалённые заметки, ретеншн 30 дней | не индексируется; восстановление возвращает файл на место |
| `_assets/` | вложения `_assets/YYYY/MM/<ulid>.<ext>` | индексируется как вложения, не как заметки |

Любые другие папки и файлы, начинающиеся с `.`, парсер также пропускает.

### 3.2 Вложенность: правило `_index.md` (Р2)

- Лист — обычный файл `Тёмная тема.md`.
- При появлении **первого ребёнка** выполняется атомарная транзакция: `Идея.md` → `Идея/_index.md`, дети создаются внутри папки. Входящие ссылки не ломаются: идентичность заметки — её `id`.
- Обратного схлопывания по умолчанию нет (папка без детей остаётся папкой).
- Отображаемое имя `Идея/_index.md` — имя папки `Идея`; поле `title` во frontmatter имеет приоритет.
- Имя `_index.md` зарезервировано: обычную заметку так называть нельзя.
- Порядок детей — поле `sort` (дробное число; перестановка = правка одного файла). Нет `sort` — алфавит по нормализованному имени (§9.3), ordinal-сравнение.

### 3.3 Журнал (daily notes)

`Journal/YYYY/MM/YYYY-MM-DD.md`, `type: journal`, без `status`. Заголовок первого уровня — дата.

## 4. Файл заметки

Markdown (CommonMark + GFM) + YAML-frontmatter в начале файла.

```markdown
---
id: 01KWKK9PHRG3EBGPKXNQ3M2EP2
type: note
title: Тёмная тема
aliases: [dark-mode]
tags: [дизайн, mvp]
status: shaping
priority: high
due: 2026-07-10
rel:
  part_of: ["[[Приложение заметок]]"]
sort: 3.5
created: 2026-07-03T12:00:00+03:00
updated: 2026-07-03T14:30:00+03:00
x-любое-поле: значение
---
Тело в markdown. Абзац с якорем. ^b3k9q
```

### 4.1 Грамматика frontmatter

- Frontmatter — блок между строкой `---` (первая строка файла, после опционального BOM) и следующей строкой `---`. Отсутствие блока валидно.
- Содержимое — YAML 1.2. Ядро использует только скаляры, списки и вложенные словари.
- **Битый YAML не делает файл невалидным**: файл трактуется как заметка без frontmatter (весь текст — тело), проблема подсвечивается в UI. Пользовательский текст не теряется.
- Неизвестные поля сохраняются как есть и доступны через индекс (`props JSON`).

### 4.2 Ядро полей

| Поле | Формат | Применимо | Семантика |
|---|---|---|---|
| `id` | ULID, 26 симв. Crockford base32 | все | Идентичность заметки. Неизменяемый. Выдаётся приложением при создании; файлу извне — при первой индексации. Сравнение регистронезависимое, канон — верхний регистр |
| `type` | `note` \| `plan` \| `project` \| `task` \| `journal` | все | Нет поля → `note`. Неизвестное значение → трактуется как `note` + мягкая подсветка |
| `title` | строка | все | Отображаемый заголовок. Нет поля → имя файла без `.md`; для `_index.md` — имя папки. Спасает заголовки с запрещёнными в Windows символами |
| `aliases` | список строк | все | Альтернативные имена для резолвинга ссылок |
| `tags` | список строк | все | Объединяются с инлайн-`#тегами` тела (индекс хранит объединение) |
| `status` | словарь §5 | note, project, plan, task | Нет поля → статус не задан (UI показывает как Входящие-кандидата, индекс хранит null) |
| `priority` | `low` \| `normal` \| `high` \| `urgent` | все, кроме journal | Нет поля → приоритет не задан (эквивалент normal в сортировках) |
| `due` | `YYYY-MM-DD` | note, project, task | Срок. Локальная дата без времени и таймзоны |
| `scheduled` | `YYYY-MM-DD` | note, project, task | Запланированная дата начала |
| `goal` | строка | plan | Формулировка цели плана |
| `target_date` | `YYYY-MM-DD` | plan | Целевая дата плана |
| `rel` | словарь: тип связи → список wiki-ссылок | все | Типизированные связи, §9.5 |
| `sort` | число (допустима дробь) | все | Порядок среди детей одного родителя |
| `created` | ISO 8601 с оффсетом | все | Момент создания. Пишется приложением |
| `updated` | ISO 8601 с оффсетом | все | Момент последней правки приложением. mtime не доверяем |
| `x-*` | любой YAML | все | Произвольные пользовательские поля. Префикс `x-` гарантирует отсутствие конфликта с будущим ядром |

Даты-дедлайны (`due`, `scheduled`, `target_date`) — строго `YYYY-MM-DD`. Метки времени (`created`, `updated`) — ISO 8601 с явным смещением (`2026-07-03T14:30:00+03:00`).

Схемы полей по типу заметки — `.graphite/types.yaml`; валидация **мягкая**: несоответствие подсвечивается, но никогда не блокирует чтение/запись.

## 5. Статусы (единый канон, Р3)

| Тип | Словарь | Переходы |
|---|---|---|
| `note`, `project`, `plan` | `inbox → shaping → planned → active → done`; `iced` | `iced` — из любого статуса; разморозка → `shaping`. Переход — только явной командой человека или ассистента; ассистент понижение не делает, повышение — предлагает |
| `task` (файл и инлайн-чекбокс) | `todo → doing → done`; `dropped` | `task_check` — set-семантика, не toggle |
| `journal` | — | без статуса |

Русские подписи: Входящие · Проработка · План · В работе · Готово · Лёд. «Пауза» проекта = `iced`, отдельного значения нет.

### 5.1 Соответствие символа чекбокса статусу задачи

| Чекбокс | Статус |
|---|---|
| `[ ]` | `todo` |
| `[/]` | `doing` |
| `[x]`, `[X]` | `done` |
| `[-]` | `dropped` |

Любой другой символ в скобках — не задача (строка остаётся обычным текстом списка).

## 6. Заголовки и блочные якоря

- Заголовки — только ATX: `#`…`######`. Setext-заголовки (`===`/`---` под строкой) в v1 не распознаются.
- Блочный якорь — `^` + идентификатор в конце строки блока, отделён пробелом: `Абзац с якорем. ^b3k9q`.
- Грамматика якоря: `^[a-z0-9][a-z0-9-]{1,31}`. Якоря задач — подмножество с префиксом `t-` (§7).
- Якорь уникален в пределах файла; при дубликате действует первое вхождение, дубликат подсвечивается.

## 7. Инлайн-задачи (Р22)

Единый синтаксис в любой заметке:

```
- [ ] Выбрать платформу @due(2026-07-15) @p(high) @every(mon) ^t-8f2k
```

### 7.1 Грамматика

```
задача     = отступ маркер " [" state "] " текст-с-аннотациями [" " якорь]
маркер     = "-" | "*" | "+" | число ("." | ")")
state      = " " | "/" | "x" | "X" | "-"
аннотация  = "@due(" YYYY-MM-DD ")" | "@p(" low|normal|high|urgent ")" | "@every(" выражение ")"
якорь      = "^t-" 4*6(Crockford base32, нижний регистр)
```

- Аннотации распознаются в любом месте строки после чекбокса; канонично — в конце. **Текст задачи** = строка без аннотаций и якоря, лишние пробелы схлопнуты, края обрезаны.
- Якорь — строго последний токен строки. Стабильный адрес задачи = «файл + якорь»; проставляется ядром при индексации, если отсутствует (для задач планов — обязателен).
- `@every(…)` зарезервирован: парсится и сохраняется как непрозрачная строка, исполняется в v2.
- Вложенные чекбоксы (отступ 2+ пробела или таб) — самостоятельные задачи; вложенность не влияет на их учёт.
- Агрегация прогресса — без двойного счёта: каждая задача учитывается один раз по файлу-источнику; зеркала не считаются.

### 7.2 Зеркала

`![[План MVP#^t-8f2k]]` в другой заметке рендерится живым чекбоксом; клик пишет в файл-источник (v1).

## 8. Теги

- Инлайн-тег: `#` + идентификатор из букв Unicode, цифр, `_`, `-` и `/` (иерархия: `#вложенный/тег`).
- Тег заканчивается на первом недопустимом символе (`#tag-mix_2.` → тег `tag-mix_2`).
- Не тег: чисто числовой (`#2026`), `#` внутри слова (`слово#нет`), `#` внутри кода (§11).
- Полный набор тегов заметки = `tags` frontmatter ∪ инлайн-теги тела; сравнение тегов — по нормализации §9.3, отображение — как написано.

## 9. Связи

### 9.1 Формы wiki-ссылок

| Форма | Пример | Семантика |
|---|---|---|
| title | `[[Тёмная тема]]` | по заголовку/имени файла/алиасу |
| путь | `[[Проекты/Приложение заметок/План MVP]]` | путь от корня vault, `/` — разделитель, `.md` опционален |
| секция | `[[Тёмная тема#Палитра]]` | к заголовку внутри заметки (один уровень `#`; цепочки `#A#B` зарезервированы) |
| блок | `[[Тёмная тема#^b3k9q]]` | к блоку по якорю |
| с текстом | `[[Тёмная тема\|как красят тьму]]` | отображаемый текст после `\|`; комбинируется с секцией/блоком |
| id-форма | `[[id:01KWKK9PHRG3EBGPKXNQ3M2EP2]]`, `[[id:01KWKK…\|текст]]` | по ULID; рекомендована агенту — железно стабильна. Секция в id-форме зарезервирована |
| эмбед | `![[Заметка]]`, `![[Заметка#Секция]]`, `![[План#^t-8f2k]]` | трансклюзия (v1): глубина ≤5, цикл → рендер ссылкой с предупреждением |

В ячейках GFM-таблиц `|` внутри ссылки экранируется: `[[Ёжик в тумане\|ёж]]`; парсер трактует `\|` внутри `[[…]]` как `|`.

### 9.2 Порядок резолвинга

1. цель содержит `/` → точный путь от корня vault;
2. префикс `id:` → по ULID (регистронезависимо);
3. иначе → уникальный `title` или `alias` (после нормализации §9.3).

Неуникальный title: в UI — пикер, в MCP — ошибка `AMBIGUOUS` с кандидатами. Битая ссылка — валидный текст: попадает в индекс как неразрешённая, чинится отчётом «Разорванные связи» (по alias/истории переименований).

### 9.3 Нормализация при сравнении

Пайплайн (только для сравнения, файлы не меняются): **Unicode NFC → casefold → `ё`→`е` → трим краевых пробелов**.

Применяется к: цели ссылки, `title`, `aliases`, имени файла (без `.md`), тексту заголовка в `#`-адресации, тегам. Не применяется к `id` (там только регистронезависимость) и якорям (сравниваются буквально).

### 9.4 Бэклинки

В файлах не хранятся никогда (Р15) — только вычисляемая таблица `links` индекса.

### 9.5 Типизированные связи `rel:`

```yaml
rel:
  part_of: ["[[id:01KWKK…|Приложение заметок]]"]
  depends_on: ["[[Индекс SQLite]]"]
```

Реестр типов: `related` (дефолт), `part_of`, `depends_on`, `blocks`, `contradicts`, `distilled_from`, `collected_in`; кастомные — только с префиксом `x-`. Обратные представления (`has_part`, `blocked_by`, …) вычисляет индекс, в файлах их нет. Значения — wiki-ссылки любой формы из §9.1.

## 10. Вложения

- Путь: `_assets/YYYY/MM/<ulid>.<ext>`; ссылки в тексте — стандартный markdown с путём от корня vault: `![](_assets/2026/07/01KWKK….png)`. Move/rename заметок такие ссылки не ломает.
- Дедуп по blake3: совпал хэш — переиспользуется существующий файл.
- GC осиротевших — только отчётом (v1), никогда автоматически.

## 11. Что не парсится

Внутри fenced-код-блоков (``` ``` ``` и `~~~`) и инлайн-кода `` `…` `` **не распознаются**: wiki-ссылки, теги, задачи, заголовки, якоря. `[[не-ссылка]]` в коде — просто текст.

## 12. Имена файлов и Windows-края

- Лимит имени файла, создаваемого приложением, — **120 символов**: длиннее — обрезка с `…`, полный заголовок в `title`. Чужие более длинные имена читаются (long-path aware, `\\?\`-пути).
- Запрещённые в Windows символы `\ / : * ? " < > |` при создании файла заменяются на `—`; оригинал — в `title`.
- Ведущие/хвостовые пробелы и точки в именах приложение не создаёт; чужие — читает.
- Кириллица, `ё`, эмодзи и прочий Unicode в именах — полноправны.

## 13. Версионирование формата

- Текущая версия — `vault_format: 1`; фиксируется в `.graphite` (мета индекса и настройки).
- Парсер, встретивший бо́льшую версию, не пишет в vault и предлагает обновиться.
- Изменения формата возможны только через инкремент `vault_format` + миграцию; этот документ при этом не редактируется — пишется следующий.
